## 问题陈述 / Problem statement

2026-03-12 14:22，顾客订单 A10882 被客服核对时发现：青禾小店商品 KH-204 的页面售价应为 199.00，实际显示 19.90。源价格表（`prices-source.csv` 第 14 行）该 SKU 的现行售价是 199.00，成本是 86.00。同一窗口内另有 9 笔订单（A10873–A10881、A10883）以下价成交。

## 三条腿 / Three legs

### A. 发生 / Occurrence

| 问次 / Why | 回答 / Answer | 证据 / Evidence | 事实或假设 / Fact or hypothesis |
| --- | --- | --- | --- |
| 1 | 页面上的 19.90 来自改价表单在 14:05 写入的新售价，不是源价格表里的 199.00。 | 改价日志 14:05:11，操作者账号 merch-02，字段 `sale_price` 由 199.00 改为 19.90；源价格表第 14 行仍为 199.00。 | 事实 / Fact |
| 2 | 表单接受了 19.90 并直接保存。 | 改价表单校验规则：只要求数值大于 0，且最多两位小数。19.90 满足该规则。 | 事实 / Fact |
| 3 | 表单没有把新售价和成本、现行售价比较。 | 表单代码中只有「大于 0」和「两位小数」两项校验，没有成本下限，也没有降幅阈值。 | 事实 / Fact |
| 4 | 改价规则当初只写了「不能写成 0 或负数」，没有写大幅度降价怎么处理。 | 店铺《改价说明》第 2 条：售价必须为正数。全文没有成本下限，也没有降幅超过某一比例需第二人确认的条款。 | 事实 / Fact |

- 根因 / Root cause: 改价表单没有成本下限，也不拦截大幅度降价，错误售价可以被直接保存。
- 倒读检查 / Backward read: 没有下限和降幅拦截，所以 19.90 能被保存；所以页面按 19.90 展示；所以订单按下价成交。链子接得上。

### B. 发现 / Detection

| 问次 / Why | 回答 / Answer | 证据 / Evidence | 事实或假设 / Fact or hypothesis |
| --- | --- | --- | --- |
| 1 | 顾客下单后，客服对单才发现，发布前没有人拦住。 | 第一条相关客服记录是订单 A10882 在 14:22 的对单备注；14:05 至 14:22 没有改价复核记录。 | 事实 / Fact |
| 2 | 改价在保存时即写入在售目录，中间没有待审队列，也没有「上架前对一遍价格」的步骤。 | 发布流程说明第 1 步：「保存后立即在售」。系统中不存在价格待审状态。 | 事实 / Fact |
| 3 | 发布前没有把在售价格和源价格表逐条对照的检查。 | 发布清单有「商品图已上传」「库存大于 0」，没有「在售价与源价格表一致」这一项；也不存在对照脚本或测试。 | 事实 / Fact |

- 根因 / Root cause: 改价保存即上架，发布前没有把在售价格和源价格表对照，也没有必须通过的检查。
- 倒读检查 / Backward read: 保存即上架且没有对照检查，所以 19.90 能直接出现在页面上；所以第一道发现发生在顾客下单之后。链子接得上。

### C. 体系 / System

| 问次 / Why | 回答 / Answer | 证据 / Evidence | 事实或假设 / Fact or hypothesis |
| --- | --- | --- | --- |
| 1 | 店内规范写了发货和退款怎么做，但没有写改价如何审核、如何对照。 | 《日常运营清单》有发货、退款两节；目录中没有「改价」节。 | 事实 / Fact |
| 2 | 开店时把「上架商品」写成一项，却没有把「改价的门槛和对照」写成固定步骤。 | 开店清单第 6 项是「添加商品并填写价格」；其后没有改价审核、源价格表对照或降幅确认。 | 事实 / Fact |
| 3 | 价格被当成低风险字段：只要填了正数就可以卖。 | 《改价说明》第 2 条只约束正数；访谈当班改价人员（示例角色）确认：一直按这条执行，没有第二人确认的习惯。 | 事实 / Fact |

- 根因 / Root cause: 项目规范里没有改价审核、降幅确认和源价格表对照的固定步骤，价格字段事实上不受门槛约束。
- 倒读检查 / Backward read: 规范里没有这些步骤，所以表单和发布流程都没有设门槛；所以错误售价可以保存并直接在售。链子接得上。

## 停问核对 / Stop-rule check

- 三条腿都追到了能改的表单规则、发布检查和项目规范，没有停在「某个人没看仔细」。
- 若只改 KH-204 这一张价签，同类错误仍会在其他 SKU 上再发生，所以不能停在单次改价。

## 对策 / Countermeasures

| 腿 / Leg | 针对的根因 / Root cause addressed | 对策 / Countermeasure | 防止或拦住 / Prevent or catch |
| --- | --- | --- | --- |
| A 发生 / Occurrence | 表单无成本下限、无降幅拦截 | 新售价不得低于成本；相对现行售价降幅超过 30% 时，保存前必须由第二人确认，否则不能写入。 | 防止 / Prevent |
| B 发现 / Detection | 保存即上架，且无对照检查 | 发布前增加一道检查：把在售价格和源价格表逐条对照，任一 SKU 偏差超过 5%（或低于成本）则发布被卡住，不能上架。 | 拦住 / Catch |
| C 体系 / System | 规范中没有改价步骤 | 在《日常运营清单》增加「改价」节：每次改价必须有源价格表依据；大幅度降价必须第二人确认；对照检查通过后才能发布。禁止只按上一次页面价格改。 | 防止 + 写入规范 / Prevent and write into norms |

## 验收 / Verification

- 再跑原问题的结果 / Rerun of the original case: KH-204 已恢复为 199.00，页面与源价格表一致。
- 再引入原错误后，新检查是否抓住 / After reintroducing the error: 在测试目录把 KH-204 写成 19.90，对照检查在发布时卡住，并写出「KH-204 在售 19.90，源价格表 199.00，偏差超过 5%」。降幅超过 30% 且无第二人确认时，表单拒绝保存。
- 正常输入是否仍通过 / Valid inputs still pass: 将 KH-204 写回 199.00，对照检查通过；将售价改为 189.00（降幅约 5%，仍高于成本 86.00），保存和发布均通过。
- 是否带出新的问题 / Any new issues: 无。

## 写入规范与横向排查 / Standardise and look sideways

- 写进了哪里 / Written into: 《日常运营清单》新增「改价」节；改价表单增加下限与降幅确认；发布清单增加「源价格表对照必须通过」。
- 横向排查 / Sideways search: 对全部在售 SKU 与源价格表做了一次对照。本次未发现其他偏差。同时检查了优惠券和套装价两处也会改最终成交价的入口，确认同样加上限与对照，避免只挡了单品改价。
- 仍未做完的事项 / Still open: 历史 10 笔订单的补差沟通仍在进行（属止损后续，不是本类错误的根因）。

## 防错 / Error-proofing

| 字段 / Field | 内容 / Content |
| --- | --- |
| 错误类型 / Error class | 在售价格与源价格表不一致，或新售价低于成本、降幅过大却无人确认。 |
| 档次 / Level | 卡住 / Block（表单在无确认时拒绝保存；发布对照不通过则卡住）。未能做到「消除」：改价仍需人工输入，但错误价格不能直接进入在售目录。 |

## 摘要 / Summary

根因不是「这一次把小数点写错了」，而是：改价表单不拦不合理的低价，发布前不对源价格表，规范里也没有改价门槛。现在大幅度降价不能独自保存，发布前对照检查不过就卡住，并把这写成以后改价的固定步骤。再把 19.90 引进测试目录，检查确实能拦住。还没做完的是那 10 笔已下单的后续处理。
